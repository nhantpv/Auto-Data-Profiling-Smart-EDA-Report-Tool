Giải pháp của chúng tôi giải quyết vấn đề gì

Ghép đúng 3 mảnh chưa ai ghép cùng nhau (Framing D).

Element 1

Hợp đồng Finding chuẩn hóa (L3)

Một schema JSON có version, hợp nhất kiểu lỗi (TFDV) + tách metric/constraint (Deequ) + gán chuẩn DAMA-DMBOK / ISO 25012 trên từng finding.

Element 2

Verdict “sẵn sàng cho ML?” (L2→L3)

Tổng hợp các tín hiệu (missing, outlier, leakage, imbalance…) thành một phán quyết deterministic READY / WARN / NOT_READY — mở rộng IBM DQ Toolkit.

Element 3

LLM bị cấm “tính toán số” (L4)

AI chỉ được trích dẫn & diễn giải con số có sẵn trong L3, không được tự sinh số. Đây là “con hào” không vendor nào công bố.

Khác biệt cô đọng: không phải “kiến trúc mới” (cái đó thương mại đã làm) — mà là bản mã nguồn mở đầu tiên kết hợp schema chuẩn hóa + verdict ML deterministic + LLM cấm bịa số + đảm bảo tái lập.

Triết lý kiến trúc

Deterministic-First, LLM-Last.

Máy tính làm phần “sự thật”

L1–L3 thuần Python/ML/thống kê: mọi con số, mọi biểu đồ đều sinh từ engine xác định, tái lập được (seed cố định, temperature=0).

AI làm phần “diễn đạt”

L4 LLM tuyệt đối không chạm dữ liệu thô — chỉ đọc file JSON findings. Vai trò: “người đọc kết quả thống kê” + viết văn.

L3 — Trái tim của hệ thống

Hợp đồng dữ liệu: 3 file JSON Pydantic-strict.

// 1) data_quality_findings.json → Data QA Agent { "dataset_meta": { "n":891, "p_cells_missing":0.08, "n_duplicates":0 }, "columns": { "Age": { "type":"numeric", "p_missing":0.19 } }, "anomalies": [{ "issue_type":"OUTLIER_ENSEMBLE", "severity":"HIGH", "detected_by":"IForest+ECOD+LOF/avg", "dq_dimensions":["Validity"], // C1 "compound_severity":"CRITICAL", // C2 "top_10_samples":[...] }] }
// 2) schema_evaluation_findings.json → Architect { "schema_meta":{ "total_tables":3, "total_relationships":2 }, "integrity_errors":[{ "error_type":"ORPHAN_FOREIGN_KEY", "affected_table":"orders", "severity":"CRITICAL" }] }
// 3) dataset_verdict.json (mới, từ L2.5) { "dataset_verdict":{ "overall":"NOT_READY", // READY|WARN|NOT_READY "score":0.42, "top_blocking_findings":[...] } }

Tách file để LLM không bị “ngợp” context. Trường dq_dimensions / compound_severity / verdict là phần làm giàu (C1+C2) so với bản gốc 2 file.

L4 — Cơ chế chống bịa số (Guardrail)

“Cảnh vệ” Python đứng giữa LLM và sự thật.

Vấn đề

Retry-on-network-error chỉ chống lỗi mạng/format, KHÔNG chống bịa số / bịa tên cột. Đó mới là khác biệt deterministic-first thật.

Cơ chế: Allowed-Set + Tolerance + Column-Check

  1. Xây Allowed-Set: mọi số trong JSON gốc + whitelist {0,1,2,3,10,100,1000} + cho qua số năm.
  2. Regex quét MỌI số trong văn bản LLM → đối chiếu Allowed-Set với tolerance (integer: chính xác · decimal: ±0.0001 · relative: ±0.1%).
  3. Column-name check: LLM nhắc tên cột không tồn tại → hallucination.
  4. Vi phạm → retry ≤3 → thay bằng <SỐ LIỆU CHƯA XÁC MINH>. Chạy sau mỗi agent (Mini + Master).

Cam kết (đo bằng eval 50-finding)

Chỉ sốMục tiêuKill nếu
Hallucination (mọi số trong báo cáo)0%> 2%
Over-masking (mask nhầm số đúng)< 5%> 15%
Column hallucination0%—

Verify thuần Python, <5ms/report, không gọi LLM → tái lập 100%. Tách bạch với retry mạng. So sánh A/B (có vs không guardrail) = số liệu cho paper/blog.

Chấm điểm nghiêm trọng & phán quyết

Từ “1.247 lỗi” (nhiễu) → “3 lỗi CRITICAL chặn training” (tín hiệu).

Per-finding (DAMA-aware)

Bảng ngưỡng key theo (chiều DAMA × magnitude bucket), có tài liệu — thay cho rule rời rạc if missing>20% then HIGH.

Compound escalation

≥2 lỗi trùng trên 1 cột (missing + drift + outlier) → nâng 1 bậc (max-tier+1, cap CRITICAL). Điền trường compound_severity.

Dataset Verdict

Rollup có trọng số → READY / WARN / NOT_READY + điểm + danh sách lỗi chặn. File JSON thứ 3.

Quyết định kiến trúc  Cả 4 module L2.5 đều có trong v1 (runtime nhẹ: ~50+20+30+15 dòng). Chỉ việc fit bảng calibrator_table.json bằng benchmark 72 dataset OpenML-CC18 (đo tương quan với mức tụt accuracy) là hoãn sang nhánh paper. v0.1 dùng bảng đặt tay cùng cấu trúc → sau này chỉ thay nguồn số, không đổi code.

Expect đầu ra của toàn bộ pipeline

Một “lần click” → báo cáo chẩn đoán hoàn chỉnh.

📄 Artifact chính

  • Báo cáo Markdown có Executive Summary + nhận xét từng cột/bảng, chèn biểu đồ.
  • 3 file JSON findings (machine-readable, audit được).
  • File CSV dump 100% dòng rác để Data Engineer xử lý.
  • Biểu đồ overview + diagnostic (điểm rác bôi đỏ).

✅ Tính chất đảm bảo

  • 0% bịa số trên các con số có trích dẫn (đo bằng eval).
  • Tái lập: cùng input → cùng báo cáo (temp=0, hash L3 lưu kèm).
  • Verdict ML-readiness: trả lời thẳng “dữ liệu sẵn sàng train chưa?”.
  • Đa bảng: bắt lỗi khóa ngoại mồ côi giữa các bảng qua DBML.

Ví dụ kết luận máy đọc được: verdict = NOT_READY (0.42) vì 1 lỗi ORPHAN_FOREIGN_KEY mức CRITICAL ở bảng orders + cột Age có 19% missing nâng bậc cùng outlier → khối training.

C1 (schema giàu DAMA) + toàn bộ L2.5 (Verdict + Compound + MCAR/MAR/MNAR, bảng đặt tay) + C3 (guardrail Allowed-Set). Mục tiêu: tool dùng được, nhanh, đúng số.

Nhánh nghiên cứu (paper)

Fit calibrator_table.json bằng OpenML-CC18 → bảng severity có cơ sở thực nghiệm (“Calibrated severity on OpenML-CC18”). Kill nếu Spearman ρ < 0.5.

Bổ sung — những phần dễ bị bỏ qua

Rủi ro, đánh giá & phần “honest”.

⚠️ Giới hạn cần nói thẳng

  • Bảng severity v0.1 đặt tay (heuristic) — chưa được validate thực nghiệm cho tới khi fit OpenML-CC18.
  • Multimodal: claim từ “nhìn biểu đồ” (vision) guardrail số không chặn được (chấp nhận rủi ro, ghi log).
  • v1 anomaly chỉ cột số; rác đa biến categorical/cross-column hoãn v2.
  • Over-masking: Allowed-Set có thể mask nhầm số đúng → phải đo (<5%).
  • Calibration per-customer: CRITICAL của finance ≠ marketing → cần framework, không có default tuyệt đối.

🧪 Kế hoạch đánh giá (kill criteria)

  • Guardrail: hallucination 0% / over-masking <5% trên 50 finding.
  • Severity calibration: Spearman ρ(tier, Δaccuracy) ≥ 0.5 trên held-out.
  • Verdict: dataset sạch→READY; 1 orphan-FK CRITICAL→NOT_READY.
  • A/B baseline: cùng input chạy có/không guardrail → bảng số.
